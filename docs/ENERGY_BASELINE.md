# 后台能耗基线（bg E-6 / D7）

> 方法可重复、数值留待装包实测轮填写。改动前 = v08（bg 门槛落地前）构建；改动后 = bg 完成后的构建。
> 计数器仅 debug 构建存在（`debug/EnergyCounters.kt`，`BuildConfig.DEBUG` 常量折叠 + R8 消除调用），release 零开销。

## 1. 测量方法

```bash
# 1) 重置电量统计（需 root 的老版本可跳过，改用「设置 → 电量」人工读数）
adb shell dumpsys batterystats --reset

# 2) 执行固定操作序列（见下），全程亮屏/灭屏状态保持一致
# 3) 采样
adb shell dumpsys batterystats com.zhaoyingqi.payledger > _tmp/batterystats.txt
# 关注：Estimated power use (mAh)、唤醒次数（wakeup count）、后台 CPU 时间

# 4) 计数器读取：打开调试页「后台能耗计数」卡片（或重启进程前后各记一次）
```

**固定操作序列**（前后两次必须完全一致）：

1. 打开微信，收 20 条聊天消息（每条间隔约 10 秒，屏幕熄灭、应用在后台）；
2. 完成 1 笔微信付款（前台支付成功页停留约 10 秒）；
3. 打开支付宝，前台滚动浏览约 1 分钟；
4. 熄屏静置 10 分钟（无任何操作）。

**计数器口径**（调试页「后台能耗计数」）：

| 指标 | 含义 | 期望（改动后） |
| --- | --- | --- |
| 收到事件 | 目标包通知 + 无障碍事件总数 | 随操作序列线性 |
| 布局渲染 | RemoteViews `apply` 次数 | 仅付款凭证类通知 +1，聊天消息 0 |
| 窗口遍历 | 无障碍窗口树遍历次数 | 仅含付款信号的事件 >0，滚动/输入 0 |
| 读取节点 | 遍历累计 `getChild` 节点数 | 随遍历次数同步下降 |
| 影子差异 | 旧流程可入账而新流程未入账 | **必须为 0**（非 0 即门槛漏记） |

> 注意：计数器是进程内存数，进程被杀后清零；对比前后必须各自「杀进程 → 重新计数」。

## 4. 影子比对采集（bg 4.1，硬性验收）

采集至少 10 笔真实付款（微信 + 支付宝，通知与前台两条路径各覆盖）与 50 条非付款内容

影子差异非 0 时：把对应场景文案（脱敏后）与 `ParserRules.hasPaySignal` 对照，先放宽门槛关键词
再复测；不要直接放宽去重/节流参数（它们只影响时序，不影响内容判定）。

## 5. 已知边界

- `notificationTimeout` 300→500ms：首个无障碍事件最多晚到约 200ms，入账延迟可忽略（去重窗 ±10 秒）。
- 节流 1500ms 且时间戳只在通过信号门槛后刷新：含付款信号的事件不受无信号事件压制。
- 厂商 ROM 对无障碍事件裁剪不一致不在本变更范围；保持现有行为不恶化。
