## 项目约束（实现时必须遵守）

- 不申请 `INTERNET` 权限，数据只存本机 Room，不得引入任何联网/上报。
- 现有设计为"无前台服务、无轮询、事件驱动"。**若某方案需要改这条（如加前台服务保活），须先征得用户同意**，不得擅自引入。
- 金额一律用整数分（`Long`），不得改成浮点。
- 日志中不得写入通知原文等敏感内容。

## O-01 ✅ 已完成　服务销毁时取消入库协程导致漏记（P0）

**现状**
- `notification/NotificationLedgerService.kt:100-103`：`onDestroy()` 里 `scope.cancel()`。
- `notification/PaymentAccessibilityService.kt:92-96`：同样在 `onDestroy()` 里 `scope.cancel()`。
- 两个服务都在 `onNotificationPosted` / `onAccessibilityEvent` 中用 `scope.launch { save(...) }` 异步入库。

**问题**
服务被系统回收（省电杀后台、切换、升级）时，`onDestroy()` 会取消该 scope。若此时 `savePayment` 的协程尚未完成（数据库写入进行中），会被直接取消，**这笔账永久丢失**。这是"通知明明收到了却没记账"的隐形原因，比断连问题更难排查。

**建议方案**
- 在 `PayLedgerApplication` 中提供应用级 `applicationScope`（`SupervisorJob() + Dispatchers.IO`），生命周期与进程一致。
- 两个服务改为使用 `app.applicationScope` 启动入库协程，不要在服务 `onDestroy()` 中 cancel 它。
- 服务自身的 scope（若有其他用途）与入库 scope 分离。

**验收标准**
- 模拟在入库协程执行中销毁服务（可通过测试注入延迟验证），记录仍能写入数据库。
- 无障碍与通知通道都不再因服务销毁而丢账。

## O-02 ✅ 已完成　去重"先查后插"存在并发竞态（P0）

**现状**
- `PayLedgerApplication.kt:17-30`：`savePayment()` 先 `dao.findDuplicate(...)`，无重复则 `dao.insert(...)`，是两次独立 DB 操作。
- `data/TransactionDao.kt:25-26`：`findDuplicate` 单条查询，无事务包裹。

**问题**
通知通道与无障碍通道可能同时捕获同一笔支付（双通道本为互补兜底），两个协程并发执行：都查到"没有重复" → 都执行 insert → **同一笔账记两次**。

**建议方案**
- 在 `TransactionDao` 中把"查重 + 插入"合并为一个 `@Transaction` 方法（ Room 的 `@Transaction` 注解），在事务内完成判定与写入。
- 或给表增加幂等约束字段（如通知 `key` / 双通道共享的捕获标识）并建唯一索引，用 `OnConflictStrategy.IGNORE` 兜底。

**验收标准**
- 并发调用 `savePayment` 两次（同渠道、同金额、相同时间戳），数据库中只产生 1 条记录。
- 现有 ±10 秒去重行为保持不变。

## O-03 ✅ 已完成　`summary` 存储通知原文（P0，隐私）

**现状**
- `notification/NotificationParser.kt:33`：`summary = haystack.take(MAX_SUMMARY_LEN)`，而 `haystack = "$t $body"` 是标题+正文全文。
- `data/TransactionRecord.kt:13`：`summary` 注释明确"含银行卡尾号等，便于对账"。

**问题**
README 宣称"通知文本不写入日志"，但通知原文（最多 200 字，含银行卡尾号、商户、金额等）实际落到了本机数据库。这与用户强调的隐私定位存在张力——虽然仍在本机，但属于超出记账所需的最小数据范围。

**建议方案**
- 默认只存结构化字段（金额、渠道、商户、时间），`summary` 置空或仅存极简摘要（如渠道+商户）。
- 若保留原文对对账有价值，应做成**默认关闭的用户开关**，并在 README 中如实说明"原文仅本机可选存储"。
- 注意：`counterparty`（商户）由正则提取，不受此改动影响。

**验收标准**
- 默认配置下，数据库 `summary` 字段不含通知原文。
- README 隐私章节与实际存储行为一致。

## O-04 ✅ 已完成（极端 ROM 仍可能需手动）　通知服务断连后不自动重绑（P0，此前已讨论）

**现状**
- `notification/NotificationLedgerService.kt:110-113`：`connected` 是进程内静态变量，随进程死亡归零。
- `notification/NotificationLedgerService.kt:85-98`：`onListenerDisconnected()` 中调用 `requestRebind`。
- `ui/MainActivity.kt:119-132`：`ensureListenerConnected()` 在 `ON_RESUME` 时 `requestRebind`，10 秒节流。
- 用户现象：开启权限后显示已连接；退出后重进，权限仍开着却显示未连接，需重新开关权限才恢复。

**问题**
进程被杀（划后台 / 国产 ROM 回收冻结）后，系统不保证重新 bind 通知监听服务；`connected` 静态变量归零且无回调设回 true。`requestRebind` 只是"请求"，国产 ROM 常忽略，且两处调用都被 `try/catch` 吞掉，失败无感知。结果是**长时间静默漏记**，不只是显示问题。

**建议方案（按推荐顺序，改动由小到大）**
1. **用已有无障碍服务当保活锚点 + 触发重绑**（推荐先做）：`PaymentAccessibilityService` 也是系统常驻绑定，开启后进程更不易被杀；在其 `onServiceConnected()` 中主动触发通知监听重绑。
2. **状态判断改为持久化**：把"最近一次连接时间"写入 SharedPreferences，进 App 时结合授权状态判断，避免进程一死就误报"未连接"（只修显示，不解决漏记，需配合方案 1）。
3. **补广播兜底**：监听 `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` / `USER_UNLOCKED` 后主动 `requestRebind`，覆盖开机与升级场景。
4. **前台服务保活（最后手段）**：挂常驻通知让进程不被回收，从根上解决。但违背现有"无前台服务"设计原则，**须先征得用户同意**。
5. 用户层缓解：引导把 App 加入 OriginOS/vivo 后台白名单（自启动 + 后台高耗电 + 锁定后台 + 关睡眠待机）。

**验收标准**
- 在 iQOO OriginOS 6 上，杀掉 App 进程后重进，`connected` 状态正确恢复，无需手动开关权限。
- 杀死进程期间发生的付款通知仍能被记录（或明确记录"该场景依赖方案 4"）。

## O-05 ✅ 已完成　金额提取可能抓错（P1）

**现状**
- `notification/NotificationParser.kt:44-57`：`extractAmountCents` 取全文第一个 `¥` 前缀，其次第一个 `…元` 后缀。
- `notification/ParserRules.kt:29-30`：对应正则。

**问题**
通知文案可能同时含付款金额、红包、优惠、积分抵现等多个金额（如"付款成功 ¥50，获得 ¥5 红包"）。当前逻辑会抓到全文第一个 `¥`，若第一个不是实际付款金额则记错账。

**建议方案**
- 优先在付款关键词（"付款成功"/"支付成功"/"已扣款"等）附近窗口内匹配金额，而非全文。
- 明确排除红包/优惠/积分等修饰词紧邻的金额。
- 补充真实通知样本到单元测试（debug 页可采集原文），用测试驱动正则调整。

**验收标准**
- 单测覆盖"付款金额 + 红包金额"等混合文案，提取结果正确。
- 现有 421 个用例（或当前测试集）全部通过。

## O-06 ✅ 已完成　去重规则两头不讨好（P1）

**已实施方案（v06 迭代）**
- 判重窗口改按采集时间 `capturedAt`（恒为到达/事件时间），交易时间 `occurredAt` 只用于展示与统计。
- 候选重复（同渠道同金额、采集窗 ±10 秒）交纯函数 `DuplicatePolicy` 判定：商户不同或双方明确交易时间相差 ≥1 秒视为不同笔，其余判重。
- 存储层兜底：`dedupKey = sha256(渠道|金额分|商户|交易时间分)` 前 16 位 + 唯一索引 + `INSERT IGNORE`，极端并发也只落一条。
- 单测覆盖：四类判定用例、去重键稳定性、100 并发同笔只落 1 条。

**验收标准**
- 同额不同商户的两笔短间隔消费均被记录（DuplicatePolicy 商户信号）。
- 同一笔支付经双通道捕获只记一次（时间信号 + dedupKey 兜底）。

**现状**
- `notification/ParserRules.kt:39-43`：`DedupWindow.WINDOW_MS = 10_000L`（±10 秒）。
- `PayLedgerApplication.kt:19`：仅按 `channel + amountCents + 时间窗` 判重。

**问题**
- **漏记**：±10 秒内两笔同渠道同金额消费（如连买两个 20 元商品）会被误判为重复。
- **重记**：通知延迟超过 10 秒的同一笔（无障碍与通知通道时间差过大）会重复入库。

**建议方案**
- 判重键加入 `counterparty`（商户名）或通知唯一标识（如 `StatusBarNotification.key`），区分"同额不同商户"与"同笔不同通道"。
- 双通道共享一个捕获标识（如按交易时间+金额+商户生成 hash），作为幂等键。
- 时间窗可按通道差异化放宽，但需权衡。

**验收标准**
- 同额不同商户的两笔短间隔消费均被记录。
- 同一笔支付经双通道捕获只记一次。

## O-07 ✅ 已完成　`occurredAt` 用通知到达时间（P1）

**已实施方案（v06 迭代）**
- 新增 `PaymentTimeParser`：从文案解析交易时间（`yyyy-MM-dd HH:mm[:ss]`、`M月d日 HH:mm`、`今天 HH:mm` 三种格式）。
- 解析结果必须落在信任区间 `[到达 −24h, 到达 +5min]`，超出视为不可信。
- 解析到 → 按文案时间入账（`timeEstimated = false`）；解析不到或不可信 → 回退到达时间并标记估算（`timeEstimated = true`）。
- 编辑记录时清除估算标记；调试页微信模板带付款时间，可验证两条路径。

**验收标准**
- 含明确时间的通知按解析时间入账。
- 无时间的通知回退行为与原有行为一致（回退到达时间），不产生回归。

**现状**
- `data/TransactionRecord.kt:12`：`occurredAt` 取通知到达时刻（`sbn.postTime` / `System.currentTimeMillis()`）。

**问题**
国产 ROM 通知延迟可达数分钟，跨午夜时会把交易记到错误日期，影响"今日支出"与月度归档准确性。

**建议方案**
- 优先从通知文案解析交易时间（若微信/支付宝凭证含时间戳）。
- 解析不到时回退到通知到达时间，并在 `note` 或单独字段标注"时间为估算"可选。
- 注意与 O-05 的金额提取共用同一段文案解析逻辑，避免重复遍历。

**验收标准**
- 含明确时间的通知按解析时间入账。
- 无时间的通知回退行为与现有一致，不产生回归。

## O-08 ✅ 已完成　查询 LIMIT 500（P2）

**现状**
- `data/TransactionDao.kt:17`：`observeBetween` 带 `LIMIT 500`，注释说明"MVP 不做分页"。

**问题**
单月超过 500 笔时，更早的记录在明细页不可见（汇总金额仍正确，因为 `observeSumBetween` 是独立 SUM 查询）。

**验收标准**
- 单月 1000 笔记录时，明细页可查看全部（滚动加载或一次性加载均可接受）。

## O-09 ✅ 已完成　"退款"关键词整条误杀（P2）

**现状**
- `notification/ParserRules.kt:23-26`：`IGNORE_KEYWORDS` 含 `"退款"`，命中即整条忽略。

**问题**
若一条通知文案同时含付款成功语义与"退款"字样（如营销文案、退款进度混排），会被整条丢弃，导致该笔支出漏记。

**建议方案**
- 将"退款"的忽略条件收窄为"纯退款通知"判定（如标题/开头为退款，或不含付款成功关键词）。
- 保持"收款/待支付"等其余忽略词不变。

**验收标准**
- 纯退款通知不入账。
- 付款成功且附带退款字样的通知能正确入账。

## O-10 ✅ 已完成　手动记账日期与列表信息（P2）

**现状**
- `ManualAddDialog` 仅接收金额/渠道/备注，`addManual` 内部固定使用 `System.currentTimeMillis()`。
- `RecordRow` 只显示渠道、商户、金额，未显示记录时间；日分组标题只有日期与合计。

**问题**
- 用户无法补记前几天的支出，只能先记当天再手动改（旧版编辑也不支持改日期）。
- 明细页缺少时间与笔数，查看当天流水时信息不完整。

**已实施方案**
- 手动记账与编辑记录均增加 Material3 日期/时间选择器；保存后自动跳到记录所属月份。
- 列表每条记录显示 `HH:mm`，日分组显示星期与当日笔数，跨年日期显示年份；空态提示手动记账入口。
- 日期选择不允许超过今天，时间默认为当前时刻。

**验收标准**
- 手动记账可选择任意历史日期，保存后记录出现在对应月份。
- 编辑可改日期/时间，列表时间与分组随之更新。
